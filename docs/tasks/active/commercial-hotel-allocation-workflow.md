## Goal and confirmed problems
Allocation must work directly from the hotel directory without first opening room management. The current departure loader runs only inside the room-dialog effect, silently converts failures to empty choices and truncates at 200. Creation omits capacity_per_room and net/sell snapshots, causing the schema default capacity one and zero canonical prices. API lacks input/date validation; UI permits concurrent submissions and exposes raw errors.

## Scope and domain rules
Reuse the existing allocation table, single atomic INSERT and existing room-slot synchronization; no new RPC or migration is expected. Preserve tenant-scoped manager authorization and audit successful creation. Validate real ISO dates within PostgreSQL-compatible years 0001–9999, checkout >= checkin (same-day stays remain compatible), nonnegative integer room counts, positive capacity and two-decimal NUMERIC(12,2) money. Bound this slot-generating creation request to 1,000 rooms and 100 occupants per room for downstream room-slot synchronization resource safety; this does not cap global hotel stock. Explicit capacity is required for custom labels; legacy canonical types reuse the existing capacity mapping. Legacy pricePerNight remains a net-cost alias; when both it and netPrice are supplied they must match. Canonical reservation pricing is roomCount × sellPrice for the stay, without a nightly multiplier; label this explicitly. Never infer markup: sellPrice defaults zero, preserving included accommodation. No currency conversion or global dated stock deduction. Existing package/departure currency governs prices.

## API and UX

Independent complete counted departure choices (stable departure ID tie-breaker) with truthful loading/error/retry/empty states, stale-response cancellation, locale dates and clear currency context. Existing allocation modal gets explicit capacity/net/sell inputs, BS/EN labels and validation, serialized save, pending-field/close protection and failed-draft retention. Preserve existing architecture/layout and room dialog.

Discovery clarification: room slots are synchronized through the existing atomic RPC on the room-slot read path, not generated by an allocation-insert trigger. Creation remains a single insert; acceptance exercises that subsequent synchronization explicitly. No additional multi-write RPC is justified.
